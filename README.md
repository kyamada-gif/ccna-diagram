# 計算なしの図表問題

CCNA の「束B」（出力・図・画面を読む問題）のアプリ。
`ipcalc2/` と同じ作り方（React ＋ `app.jsx` → `build.js` → `app.js`）。

**束Bは3つのアプリに分かれた（2026-08-22 オーナー）。**

| アプリ | 中身 | 分野 |
|---|---|---|
| `showread/`（ここ） | 出力を読んで当てる／図表付きの問題を覚える | 8 |
| `wordmatch/` | 言葉と意味の組み合わせ | 7 |
| `configpick/` | 足りない設定を選ぶ | 5 |

**移した12分野は、このアプリからは消してある**（`q/`・`types/`・`index.html`・`gen.js`・
`questions.js`・ホームの札）。下の説明で移した分野を例に出している所は、そのままの記録。
`node build.js` の全問カバーの見張りは、よそのアプリの `q/*.js` も読んで数える。

## いちばん大事な決まり（2026-08-20 オーナー）

> **テストは、問題集PDFに載っている問題そのものを出す。全分野で。**
> **練習は、そのテストを解けるようになるためのもの。**

これ以上でも以下でもない。ここから外れる作り方をしない。

| | テスト | 練習 |
|---|---|---|
| 中身 | **本の問題そのまま** | **その場で作る（生成問題）** |
| 1問の単位 | **本の1問＝画面の1問。分けない** | 見る所ごとに小さく割る |
| 絵（図・機器の画面） | **紙面から切り出した画像** | 作った出力・作った図 |
| 文字の出力（show出力・JSON・設定） | 紙面と一字一致の写し | その場で作る |
| 置き場所 | `q/<ブロック>.js` | 置き場所は無い。`types/<ブロック>.js` が毎回作る |

**練習に本の問題を出さない。**8ブロックすべてが生成問題になっている。
`node build.js` が毎回、練習の1問1問を本の問題と突き合わせて確かめる
（問題文が同じ／提示物が同じ／出どころの番号が付いている、のどれかがあれば止まる）。

### 札2「図表付きの問題を覚える」は、過去問をそのまま覚える（2026-08-22 オーナー）

**規則を組み立てて解く題材ではないので、本の問題を1問ずつ覚える。**
`app/`（CCNA 暗記アプリ）の覚える画面と同じ作り。違うのは、図や出力が付く問題があること。

```
練習をする（覚える）… 過去問を上から順に1枚ずつ。答えも決め手も最初から出ている
                提示物（図・出力。無い問題もある）
                問題文        決め手の言葉に青い下線
                選択肢        正解が緑。答えの言葉に黄色い下線
                決め手の1行   「決め手 ◯◯ → ◯◯」
                覚え方        取り違えやすい所だけ
                本の解説
                    ↓ この分野の練習をする
練習（解く）  … 同じ過去問を、答えを隠して解く。並びは毎回変わる。
                間違えたら正解するまでやり直し。バッジは付かない
                    ↓ この分野のテストを受ける
テストを受ける … 同じ過去問で採点する（いままでどおり。9割でバッジ）
```

| 分野 | 過去問 | 紙面の図がある |
|---|---|---|
| 無線の画面を読む | 13問 | 13問 |
| 繋がらない原因を探す | 5問 | 2問 |
| その他 | 11問 | 6問 |

**決め手と答えの言葉は `points/<分野>.js` に書く。**

```js
P["B1-P11-054"] = {
  q: ["デバイスの数を 125 に制限"],        // 問題文か提示物に一字一句ある言葉
  a: ["Maximam Allowed Clients"],          // 正解の選択肢に一字一句ある言葉
  tip: "Per AP Radio はアクセスポイント1台あたりの上限で、別の行"   // 無くてよい
};
```

**一字一句ないと下線が引けない。**書き間違えると画面では静かに下線が消えるだけなので、
`node build.js` が毎回、29問すべてを本文と突き合わせて確かめる。

この3分野の `types/<id>.js`（判定ルール）は**残してある。**
テストの答え合わせで「この問題の決め手」を出すのに使っているため。
練習の生成問題は、画面からは出なくなった。

### 練習の形（全ブロック共通）

```
覚える1枚（learn）  … その見る所は何か・どう使うか
      ↓
その所の問題2問（step）… その所だけで決まる問題を、その場で作る
      ↓ （見る所の数だけくり返す）
最後に3問（whole）  … 提示物ぜんぶで判定／覚えた組み合わせで結ぶ
```

**最後の確認項目では、決まる問題を2問出す。**
そこまで来たら必ず決まるので「次へ進む出力」が作れず、2問目が空になっていた
（ルートブリッジの MACアドレス、代表ルータのルータ ID、show interface の duplex）。
`engine.js` の `stepQ` が、決まらない出力を作れないときは決まる問題をもう1問作る。

**説明の1枚で見せた形は、練習の問題にも必ず出す。**
出しようがない（作る仕掛けが無い）と、見せただけで一度も解かないままテストに出る。
実際に3つあった。

| 分野 | 見せていたのに出なかった形 | 直し方 |
|---|---|---|
| show interface | `line protocol is down` | `MAKERS` に `linkdown` を足した |
| OSPF の代表ルータ | ルータ ID の行が無く、Loopback や IP アドレスで決まる図 | 図を作るときに、書き場所を3通りから選ぶ |

ブロックの作りは `kind:"rules"` だけ。8ブロックとも、見る所を上から順に見て、
規則で答えを出す（中身は `types/<id>.js` に書く）。

言葉と説明の対を覚える `kind:"match"` は `wordmatch/` へ移した。
`engine.js` に `makeMatchEngine` は残っているが、**このアプリでは使わない**
（`gen.js` の `MATCH_IDS` は空）。

`build.js` が毎回、この決まりを機械で確かめる（下の「見張り」）。

```
showread/
  index.html      画面の地。文字7段・余白6きざみは ipcalc2 と同じ
  engine.js       共通の仕掛け。makeEngine（規則）。makeMatchEngine は使っていない
  gen.js          engine と types を組み立てるところ
  types/<id>.js   ブロックごとの見る所・判定ルール・出力の作り方（8ブロックぶん）
  questions.js    問題の入れ物。中身は q/ に置く
  q/<id>.js       **テスト用の過去問。**本の1問＝1件
  points/<id>.js  過去問1問ずつの「決め手 → 答え」。札2「図表付き」の3分野だけ
  img/<qid>.png   紙面から切り出した提示物
  img/index.js    qid → 画像の表。**画面はこれを引く**（問題データに画像を書かない）
  app.jsx         画面。ここは直す。判定も問題作りもしない
  app.js          自動生成。手で直さない
  build.js        app.jsx → app.js ＋ 検査
  vendor/         React（ipcalc2 からコピー）
```

## 画面の言葉の決まり

### 画面は2つだけ

```
ホーム（分野が20行）
  └ 行を押すとその場で開き、[練習をする][テストを受ける]
       └ 練習 or テスト（1画面1問）
            └ 結果
```

**「分野を選ぶ画面」は作らない。**ホームの行がそのまま入口になる。
練習もテストも、**ホームから2タップで1問目**が出る。

行を開くのは1つだけ（もう一度押すと閉じる）。
20行ぶんのボタンを最初から全部出すと、どこを見ればいいのか分からなくなる。

4つの札（1〜4）は、**押せない小見出し**として行のかたまりを区切るだけ。

### 名前の付け方（`app.jsx` の上のほうに1か所でまとめてある）

| もの | 書き方 | 例 |
|---|---|---|
| 札 | 番号＋名前 | `1 出力を読んで当てる` |
| 分野 | 札.分野＋名前 | `1.1 show interface の障害` |
| やり方 | 「練習」「テスト」 | **テストは分野に1本。回の番号は無い** |

### 印（バッジ）の決まり

3つの状態しかない。**どの画面でも同じ見た目**（`Mark` の1か所）。

| 状態 | 見た目 | いつ |
|---|---|---|
| まだ | 破線の空の枠 | 一度も受けていない |
| 途中 | 枠の下に最高点「28 / 31」 | 受けたが、まだ届いていない |
| 届いた | 🏅 | 届いた |

**数えるものは分野のバッジ1種類だけ。**分野は8ある。
ホームの上に「🏅 n / 8 分野」と出す。札にバッジは付けない。

前は「回ごと（38個）→ 分野（21個）→ 札（4個）」の3段だった。
数え方が3つあると、何を集めているのか分からなくなる。

### バッジが付く線は9割

`passLine(len) = Math.ceil(len * 0.9)`。**例外を作らない。**

| 本の問題 | 正解が必要な数 |
|---|---|
| 31問 | 28問 |
| 31問 | 28問 |
| 10問 | 9問 |
| 9問以下 | 満点（オーナーの判断でそのまま） |

### 画面の言葉は、講義でそのまま使える日本語にする

**分かりやすくするつもりで、ふだん使わない言い方に置きかえない。**
オーナーとの会話で使うのと同じ、普通の日本語で書く。説明的でよい。

| 書かない | 書く | なぜ |
|---|---|---|
| くらべる・こわれる・しくじる | 比べる・壊れる・失敗する | 常用漢字をひらがなにしない |
| 住所 | IP アドレス | 自分で作った言いかえは、かえって分かりにくい |
| 合言葉 | 事前共有キー | 同上 |
| 載せる先 | 所属させるインターフェース | 同上 |
| 代表になりたい度合い | 代表に選ばれやすさを決める設定値 | 機器は「なりたい」と思わない |
| 〜を打つ | 〜を入力する | 話し言葉に寄せない |
| 〜の話 | 〜について | 同上 |
| 最も大きい数 | 優先度の値が最も大きいルータ | **何の数かを必ず書く** |
| `コマンド` | コマンド | バッククォートは画面にそのまま文字として出る |

`node build.js` が `spots` `rules` `gloss` `name` `note` `ask` を見て、
左の列の言い方が残っていたら止める。

### 書きかけの印を残さない

覚え書き（コメント）では `**ここが大事**` と書いてよいが、
**画面に出る文字列に書くと、記号ごと表示される。**
`node build.js` が `spots` `rules` `gloss` `name` `note` `ask` と
`app.jsx` の画面の文を見て、`**` が残っていたら止める。
**説明の1枚（`brief`）の中の文も見る。**ここは死角で、実際に書いてしまったことがある。

### 先へ進むボタンの置き場所

**本文のすぐ下に置く**（`.dock` は `position: sticky; bottom: 0`）。
本文が短いときは内容のすぐ下に、長いときは画面の下に貼りつく。
前は画面の下の段に固定していたが、本文が短いと
「ぽつんと下に離れたボタン」になって分かりにくかった。

### 練習の問いは、いつも「本物の問い」

**「ここで決まりますか」のようなメタな聞き方をしない。**
何を目指しているのか分からないまま進み方だけ聞かれても、答えようがない。

**その分野が最後に答えるべき問い（`spec.ask`）を、確認項目1つ目から出す。**
代わりに、**選択肢に「◯◯だけでは決められない」を混ぜる。**
その選択肢が、次の確認項目へ進む思考をそのまま教える。

```
説明の1枚   優先度が最も小さいスイッチが1台 ▼ そのスイッチがルートブリッジ
            → 見た人は「優先度で選べばいいんだ」と理解する

問題1       この構成の中で、どのスイッチがルートブリッジになりますか。
              SW1 ／ SW2 ／ SW3 ／ ブリッジ優先度 だけでは決められない
            ※ 優先度が1台だけ小さい図 → 学んだことを使って答える

問題2       同じ問い。優先度が並んでいる図
            → 「ブリッジ優先度 だけでは決められない」を選ぶ
            → 次が要ることに気づく

確認項目2    優先度が並んだ ▼ MACアドレスが小さいほう
問題3       同じ問い。優先度が並んだ図 → MAC の小さいほうを答える
```

こうすると「まず優先度、次に MAC」という思考が、**問いを解くだけで積み上がる。**

- **最後の確認項目では「決められない」を出さない。**そこまで来たら必ず決まるので、
  出すと正しくない選び方を教えてしまう
- **決まる問題にも「決められない」を混ぜる。**決まらない問題にだけ出すと、
  「この選択肢が見えたらそれが正解」と形で覚えられてしまう
- `spec.ask` を持っていない分野は、`node build.js` の前に足すこと

#### 「見ている所を丸ごとふくむ答え」も、誤答にしない

決まらない問題だけでなく、**決まる問題と最後の3問でも同じ。**

```
提示物  Hello だけが両側で違う（Dead はそろっている）
正解    Hello を、相手と同じ値にそろえる
誤答に  Hello と Dead の両方を、相手と同じ値にそろえる    ← これも直ってしまう
```

Dead はもうそろっているので、両方そろえてもやはり隣接関係は直る。読める人ほど迷う。
判定ルールの `look`（見る所）が、正解のルールの `look` を丸ごとふくんでいたら、その答えは誤答にしない。
`types/ospf.js` の `walkQ` と、`engine.js` の `wholeQ` の両方で外す。
**見る所どうしにこの関係が無い分野では、何も起きない**（実際、ほかの12分野は選択肢の数が変わらなかった）。

逆に、**その確認項目自身の答えは、決まらない問題の誤答に使ってよい。**
そこで決まらない出力だと分かって作っているので、選んでも何も直らない。
前はこれを外していたので、選択肢が3つしかない問題ができていた（OSPF の練習の 4.9%）。

#### 「◯◯だけでは決められない」の名前が長すぎるとき

確認項目の名前をそのままつなぐと、選択肢が長くなる
（「txload と rxload と input errors と CRC だけでは決められない」）。
分野が `spec.short`（判定ルールの key → 短い名前）を持っていれば、そちらを使う。

#### 正解が2つある問題を作らない（**踏みやすい**）

「決められない」が正解の問題でも、**提示物には後の決め手が写っている。**
ルートブリッジの図には MACアドレスも書かれているので、
優先度が並んだ図で「決められない」と SW3 の両方を選択肢に出すと、
**MAC の決まりを知っている人は SW3 を選ぶ。それも正解**になってしまう。

実際に作ってみたところ、**400 回中 300 回**でこの形になっていた。

対策は1つ。**決まらない問題の誤答に、最後まで見たときの答えを入れない。**
`node build.js` が毎回、全分野で 40 回ずつ作って確かめる。

### 問題文が決め手になる分野の問い方

**どこを探すか → 何を答えるか**の2段。

```
1問目  この問題文の中に、答えを決める言葉があります。どれですか。
2問目  決め手は「接続できる台数を制限する」です。画面のどこを触りますか。
```

2問目の聞き方は分野ごとに変える（`E.cueStepQ(RULES, "◯◯はどれですか。")`）。
渡さなければ「この要件を満たす設定はどれですか。」になる。
**つながらない原因は「何をしますか」ではなく「原因はどれですか」**のように、
その分野が本当に聞いていることに合わせる。

#### この形の分野では、上から順に絞るやり方を使わない（2026-08-21）

**絞り込みではないので、「この確認項目では決まらない提示物」という考えが無い。**
ところが前は、共通の作り方が2問目にそれを出していた。その結果、
問1で「答えを決めているのはどれか」を教えた直後に、
**問題文を読むと別の答えに見える提示物**で解かせていた（8分野の 83%）。

```
前）問1「束の 2 番目のメンバーを正常にバンドルするには…」→ 許可VLAN が正解
    問2「相手側の設定はこうなっています…」        ← 別の問題文なのに、許可VLAN が正解

後）問1・問2とも同じ問題。値だけ作り直す
```

`engine.js` の `cueStepQ(rules, ask2)` が、この形の練習を作る。

- 問1 … その確認項目の提示物＋決め手 4択
- 問2 … 同じ確認項目の提示物（値は作り直す）＋答え 4択
- **ルールは key で引く。**答え（`verdict`）で引くと、答えが同じルールが2本あるとき
  別のルールの決め手が正解になる（EtherChannel の vendor と peer、トランクの access2trunk と totrunk）
- 誤答は、ほかのルールの決め手・答えから採る。**こちらで文を作らない**

問1の聞き方は「**この問題で、答えを決めているのはどれですか。**」。
「この問題文の中に」とは言い切らない。**決め手が出力の中にある分野がある**ため
（EtherChannel の「相手のモード」6問、トランクの「Administrative Mode が static access」など8問）。

### 答え合わせは短く。説明の1枚は詳しく

**書き分ける。**

| どこ | 何を書くか |
|---|---|
| 説明の1枚（`brief` の `note`） | 初めての人向け。見本を指して具体的に |
| 答え合わせ（`answerNote` / `st.why`） | **答えるのに必要な判断のもとだけ** |

答え合わせに判定ルールの理由（`why`）をそのまま出すと、要らない話まで並ぶ。

```
悪い  show の出力では Timer intervals configured で始まる行に、数字が4つ並ぶ。
      その1つめが Hello。すぐ下にある Hello due in の行は、次の通知までの
      残り時間なので別のもの。設定では ip ospf hello-interval の行。…

良い  設定では ip ospf hello-interval の行。
      show の出力では Timer intervals configured の行の1つめの数字
```

問いを作る側（`spec.walk`）が `why` を返すと、答え合わせの文を差し替えられる。
`null` を返すと、その分野の一言の説明（`gloss`）が出る。

**練習もテストも、同じ短い形。**前はテスト（本の問題）だけ古い長い形
（判定ルールの理由 ＋ 見た所と数の一覧 ＋ ほかが消える理由）のままで、
show interface では「ほかが消える理由」だけで8行並んでいた。
分野が `spec.answerNote` を持っていれば、テストの答え合わせもそちらを使う。

**本の解説は、文の途中で切らない。**前は150字で機械的に切っていた（`trimBook`）。

`node build.js` が毎回、90字を超える答え合わせが無いかを確かめる。
**練習の問題だけでなく、テストの過去問1問1問も見る。**

### テストの選択肢が「打つコマンドの並び」なら、練習にもその形を出す

OSPF の隣接関係は、本の7問のうち**6問の選択肢が打つコマンドの並び**だった。
ところが練習の選択肢はすべて日本語の行動文で、「どこが違うか」で止まっていた。
テストでは**どの値に合わせるか**まで要るのに、値を選ぶ所を一度も通らない。

そこで、練習の最後の3問のうち**2問をコマンドの並びで答える形**にした。

```
R2 に、どの設定を適用しますか。

  R2(config)#interface g0/1              ← Hello はもうそろっている値。何も直らない
  R2(config-if)#ip ospf hello-interval 10

  R2(config)#router ospf 1001            ← 正解
  R2(config-router)#no router-id 2.2.2.2
```

**誤答の顔ぶれは、本の4つをそのまま写す。**こちらで考え出さない。
（そろっている側の値に直す／router-id を設定する／相手と違うエリアで network を足す）
本の罠（B1-P12-061）も同じ形で、正解が `dead-interval 40` のときに
「`hello-interval 10`」＝そろっている側の値、が誤答に並ぶ。

**誤答が正解になっていないか、1つずつ確かめること。**
「片側で OSPF が動いていない」問題では、`router ospf` ＋ `network …… area` を足すのも
本来は正しいやり方なので、**そちらの誤答は必ず相手と違うエリア番号にする**
（本の B1-P12-087 も、正解が area 1 で誤答が area 0 という作りになっている）。

分野が `spec.wholeQ(n, ctx)` を持っていれば、最後の3問を自分で作れる。
`n` は何問目か（0・1・2）。`null` を返すと、いままでどおり共通の形になる。

### 決め手型の分野も、最後の2問はコマンドの並びで答える（2026-08-21）

本の選択肢がどんな形かを数えたところ、分野で分かれた。

| 分野 | コマンドの形 | 日本語の文 |
|---|---|---|
| EtherChannel | 20 / 20 | 0 |
| 機器への入り方 | 10 / 10 | 0 |
| トランクと VLAN | 17 / 19 | 2 |
| DHCP・NAT・NTP | 5 / 9 | 4 |
| ポートの守り | 3 / 4 | 1 |
| 無線の画面を読む | 0 / 13 | **13** |
| 繋がらない原因を探す | 1 / 5 | 4 |
| その他 | 1 / 6 | 5 |

**上の5分野だけ**、練習の最後の3問のうち2問をコマンドの並びにした。
下の3分野は本の選択肢が日本語の文なので、いままでの形が正しい。
DHCP・NAT・NTP の中でも、NAT の問題だけは本の選択肢が日本語の文なので
（「NAT外部インターフェイスを設定する」）、そこだけ `cmdSet` が `null` を返す。

**誤答は本の同じ問題が出しているものを写す。**こちらで考え出さない。
分野は `cmdSet(key, v)`（答えと誤答の組）と `cmdMark[key](opt, v)`
（その答えだけが当てはまる印）を持つ。`node build.js` が全ルールを 20 通りずつ作り、
**印に当てはまるのが正解1つだけ**かを毎回確かめる。

印は**打つ場所まで見る**こと。「許可VLAN を add で足す」は、
物理インターフェースに打つのが正解で、ポートチャネルに打つのは誤答。
`allowed vlan add` があるかだけでは分けられない（実際に見張りに捕まった）。

### 「どの行を見ますか」は、答えたあとに その行を光らせる

答える前は光らせない（答えが見えてしまう）。
**答えたあとに、出力の中でその行を光らせる。**どこにあったのかが、そこで初めて目で分かる。

仕組みは分野ごとに書かない。**答え（`right`）が提示物の中の1行と同じなら、その行を光らせる**
という形にしてあるので、どの分野の「どの行を見ますか」でも効く。

### 読み取った値の札は出さない

問いが本物の問いになったので、**値を抜き出して見せると読む練習ごと答えを渡してしまう。**
「その優先度のルータ 1 台」と出ると、答えが決まることまで先に分かってしまう。

決め手の語は提示物の中で光るので、どこを見るかは伝わる。
数字は答え合わせで出す（`spec.answerNote` の `body`）。

### 説明の1枚の見本は、その決まりが目で見える形にする

判定ルールが「両側を見比べる」話なら、**見本も2台出す。**
1台だけ見せて「片側に…が無い」と書いても、どこの何を言っているのか分からない。

```
【R1 の設定】                    【R2 の設定】
 …                               …
router ospf 1                    （router ospf の行が無い）
 network 192.168.30.1 … area 0

        片側に router ospf の行が無い
             ▼
   動いていない側で、相手と同じエリア番号の OSPF を有効にする
```

**`if` に書く目印は、その見本に実際に出ているものにする。**
見本が設定の形なのに「Process ID の行が無い」と書くと、画面と合わない。

### 答え合わせも、並べられるものは箇条書きにする（2026-08-22 オーナー）

**説明の1枚と地続きにする。**同じ形で書くと、覚えた見方がそのまま答え合わせで使える。

```
前）設定では network の行の末尾。show の出力では Internet address の行の末尾

後）【設定で入れるとき】
    ・network 192.168.30.1 0.0.0.0 area 0　＝ 末尾の area が番号
    【show の出力で見るとき】
    ・Internet address is 192.168.30.1/24, Area 0　＝ 末尾に出る
```

値は**説明の1枚の見本と同じ所から作る。**「さっき見た設定が、show ではこの行に出る」と目でつながる。

| どこ | 前 | 後 |
|---|---|---|
| 値が2つ以上ある所（show interface・OSPF・ルートブリッジ・代表ルータ） | 「duplex は Full、collisions は 233」 | `・duplex ＝ Full` `・collisions ＝ 233` |
| 決め手型の8分野のテスト | 「決め手は「◯◯」」＋一言 | 【この問題の決め手】→【だから、こうする】 |
| 値が1つだけの所（JSON など） | そのまま | 変えない |

**90字の決まりは、文章の答え合わせだけに当てる。**
90字は「文章がだらだら並ぶ」のを防ぐための決まりで、箇条書きは字数が増えても読むのは速くなる。
箇条書きの答え合わせは **6行まで・見出し30字・行40字**で見る。
**引用している行（コマンドや出力）は数えない。**機器が出す文字なので、長さをこちらで決められない。

### 一言に、並べて見比べるものが2つ以上あるときは、箇条書きにする（2026-08-22 オーナー）

**文章のままだと、読む人が頭の中で並べ直すことになる。**

```
前）R1 には router ospf 1 と network …… area 0 の2行がある。R2 にはこの2行が
    無いので、R2 にも同じ2行を足す。この形は設定でしか見えない。…

後）【R1 の設定】
    ・router ospf 1                        ＝ OSPF を動かす
    ・network 192.168.30.1 0.0.0.0 area 0  ＝ エリア番号を決める
    【R2 の設定】
    ・この2行が無い。R2 にも同じ2行を足す
    ───────────────────
    この形は設定でしか見えない。OSPF が動いていない側は、
    show ip ospf interface に何も出ないため
```

**並べるものが2つ以上あるときだけ**、`note` を文字列ではなく `{ rows: […] }` で書く。
「既定は 32768」のような**1つの事実だけの一言は、文のまま**でよい。
全部を箇条書きにすると、縦に伸びるだけで読みにくくなる。

| 書き方 | 画面に出る形 | 使う所 |
|---|---|---|
| `{ h: "R1 の設定" }` | 【R1 の設定】 | 機器や画面の名前 |
| `{ c: "router ospf 1", m: "OSPF を動かす" }` | ・router ospf 1　＝ OSPF を動かす | 値と、その意味 |
| `{ c: "R1  5" }` | ・R1  5 | 見比べる値だけ |
| `{ t: "この2行が無い" }` | ・この2行が無い | コマンドでない行 |
| `p: "…"` | 区切り線の下に1行 | 箇条書きにならない補足。無くてよい |

- **`・` と `＝` は画面が付ける。**データに書くと二重になる
- `＝` の右は、名詞で終わる短い言葉（20字まで）。文を書かない
- 行は8行まで
- **値は見本と同じ所から作る**（`types/ospf.js` の `LV`・`LC`、`types/rootbridge.js` の `LEARN` など）。
  別々に書くと、片方を直したときにずれる

`node build.js` が毎回、行の形・記号の二重・字数を確かめ、「箇条書きの一言 n 個」と数を出す。

いま箇条書きにしてあるのは7か所。**いちばん長かった 163字・141字・135字がここに入っていた**
（OSPF の隣接関係5つ・ルートブリッジ・OSPF の代表ルータ）。

### 決め手型の分野の見本は、決め手が出力の中にあるときだけ出す

決め手が**問題文の中**にあるルールが33、**出力の中**にあるルールが13だった（実測）。
問題文の中にあるものは、説明の1枚の「もし」の行にその言葉がもう大きく出ているので、
見本を足すと同じものを2度見せることになる。
**出力の中にあるルールだけ**、現物を1枚出す（`spec.learnOut` に key を並べる）。

### 答えたあとに、決め手になった言葉を光らせる

**光らせる言葉の表を手で書かない。**手で書くと、提示物に無い言葉を書いてしまい、
どこも光らないうえに、書き間違いにも気づけない。
判定ルールが「何を見て決めたか」を出す `steps()` の値を使う。
これは実際に読み取れた文字なので、**提示物に必ずある。**

値が長すぎて使えないルール（問題文まるごとが返るものなど）だけ、
ルールに `mark: ["…"]` と直接書く。**書いた言葉が提示物に出てくるかは
`node build.js` が毎回確かめる**（わざと `DHCP サーバー` と伸ばすと止まる）。

### 図で出る分野は、説明の1枚も図で出す

提示物が図の分野（ルートブリッジ・OSPF の代表ルータ）は、
**説明の1枚も同じ図にする。**前は文字4行の表だったので、
説明と問題とで値の置き場所が変わり、目の移し方を覚えられなかった。

見比べる機器の箱は、図のほうで光らせる。`learnEx` が返す図に `mark: ["SW2","SW3"]`
を入れると、その箱が光る（`fig.js`）。行や言葉を光らせる `hits` / `marks` は、
図（SVG）には行という単位が無いので効かない。**この2分野では持たない。**

### 添える一言（`note`）は、見本を指して具体的に書く

**ここだけは短くしない。**初めて見る人は「片側に router ospf の行が無い」と
言われても、見本のどこを指しているのか分からない。

```
R1 には router ospf 1 と network …… area 0 の2行がある。
R2 にはこの2行が無いので、R2 にも同じ2行を足す。
show の出力で見るときは Process ID の行が無く、
エリアは Internet address の行の末尾に出る
```

**見本の値と説明の文は、同じ所から作る。**別々に書くと、
片方を直したときにもう片方とずれる（`types/ospf.js` の `LV`）。

### 答え合わせに、まだ見ていない所の答えを出さない

`spec.answerNote(v, st)` には**いま見ている確認項目（`st`）も渡る**。
渡さないと提示物ぜんぶを見て最後の答えを出してしまい、
「line protocol を確認しました」の答え合わせに
「runts があり、CRC も collisions も 0 ＝ 不良 NIC」が出ていた。

| そのとき | 答え合わせに書くこと |
|---|---|
| ここで決まった | その決まりと、この出力の数字 |
| ここでは決まらない | **なぜ決まらないか**だけ（次にどうするかは、答えの行にもう書いてある） |

`node build.js` が毎回、決まらない問題の答え合わせに
決まりの形（`＝`）が出ていないかを確かめる。

### 説明の1枚は、短く（`spec.brief`）

**文字は読まれない。**見たらすぐ「こう来たら、こう答える」と分かる形だけを残す。

```
   1  [
   2    {"switch": "SW18", "port": "ge2/41"},   ← 見本。決め手の所だけ光らせる
   3  ]

        コロン : の 左        ← 見る所（記号そのもの）
             ▼
            キー             ← そのときの答え（大きく・緑）
         英語では key         ← 本の別の書き方だけ、小さく
```

分野が `spec.brief(block, i)` を持っていれば、この短い形になる。
返すのは `[{ if, then, note }]`。`then` は配列にすると、同じ箱の中に縦に並ぶ。

**字の大きさは、文の長さで決める**（`sizeOf()`）。決め打ちで大きくすると、
「そのスイッチがルートブリ／ッジ」のように**単語の途中で折れて読みにくい**。

| 答えの長さ | 字の大きさ |
|---|---|
| 5字まで（配列・キー） | 34px |
| 10字まで | 26px |
| 16字まで | 22px |
| それ以上（リンクが切れている（ケーブルか機器の故障）） | 17px |

あわせて `word-break: keep-all` を効かせて、かなと漢字の続きを途中で割らせない。

持っていない分野は、いままでの形（何を表すか／どう使うか／ここで決まるとき）のまま。

JSON では 108字 → 20字ほどになった。

### 日本語と英語のどちらで問われても、もう一方を添える

本は同じ答えを「配列」と刷ったり「array」と刷ったりする。
片方だけを見せると、別の決まりに見えてしまう。

**いま見せた書き方を先に出して、もう一方を括弧で添える。**

| 問われ方 | 解説に出る言葉 |
|---|---|
| 日本語 | 配列（英語表記：array） |
| 英語 | array（日本語表記：配列） |
| 両方併記 | array（配列）＝ そのまま |

説明の1枚では、大きい字ですでに「配列」と出ているので繰り返さず、
下に「英語表記：array」だけ添える。

「または」でつながず**どちらの表記かを名前で言う**。
そのほうが、初めて見る人に伝わる。

### 答え合わせの言葉も、同じ書き方にそろえる（`spec.answerNote`）

**同じことを2回書かない。**判定ルールの文と、答えの一言説明が
どちらも「開くかっこを上から数える」になっていて、2行とも同じ意味だった。

分野が `spec.answerNote(v)` を持っていれば、**決まりと、この場合の数字を別々の行**に出す。

```
        2                        ← 答え
   [ の数 ＝ 配列                ← 決まり（説明の1枚と同じ書き方）
   [ は 2 個                     ← この場合の数字
```

返すのは `{ gloss, body }`。持っていない分野は、いままでどおり
判定ルールの文（`why`）と答えの一言説明（`gloss`）をそのまま出す。

### 終わったあとの画面（結果）

練習もテストも、終わりの画面は同じ形。**上に点数、下に「次にやること」**。

### 間違えたら、選択肢の並びを変える

練習で間違えて「もう一度解く」を押すと、**選択肢の並びが必ず変わる。**

同じ並びのまま出すと、**位置を覚えて機械的に押せてしまう。**
この教材は言葉を覚えるものではなく、**判断の道すじをたどるもの**なので、
毎回いちから読み直してもらう。

- 中身は変えない。並びだけ
- 1回混ぜて元と同じ並びになったら、混ぜ直す（`reshuffle`）
- 結ぶ問題は、合っている組だけ残す形なので、この対象にしない
- **テストでは起きない。**1回勝負で、やり直しが無いため

### 間違えた確認項目だけを、もう一度

練習の記録には、1問ごとに `spotNo`（何番目の確認項目か）が入っている。
最初の答えが外れた確認項目を集め、**その番号だけで練習を組み直す**（`makeReview()`）。

- 問題はその場で作り直すので、**同じ問題は出ない**。
- 引くのは番号であって、名前ではない。
  確認項目の名前（`look` をつないだ文）は、別の項目と同じ文になることがある。
  名前で引くと、別の項目にすり替わる。

**key に分野とやり方の両方を入れる。**入れないと、

### 動くのはページそのもの（中に別のスクロールを作らない）

**これは決まりごとで、外すと拡大したときに壊れる。**

前は「画面の高さに固定した箱の中だけが動く」形にしていた
（`body{overflow:hidden}` ＋ `#root{height:100dvh}` ＋ `.wrap{overflow-y:auto}`）。
この形だと、**画面を拡大したときに本文のいちばん上まで戻れなくなる。**
拡大すると見えている範囲は小さくなるのに、箱は画面の高さのままなので、
中身がはみ出さず、動かす先が無くなるため。

いまはふつうのページと同じで、ページ全体が動く。

| もの | 決まり |
|---|---|
| `html` `body` | 高さも `overflow` も指定しない |
| `#root` | `min-height:100dvh` だけ（`height` にしない・`overflow:hidden` にしない） |
| `.wrap` | 中でスクロールさせない（`overflow-y` を付けない） |
| `.dock` | `position:sticky; bottom:0` |
| 見ている位置 | `document.scrollingElement.scrollTop`（`app.jsx` の `nowY` `toTop`） |

`.dock` は sticky なので、本文が長いときは画面の下に貼りつき、
短いときは本文のすぐ下に置かれる。

**`position:fixed` は使わない。**fixed は「目に見えている範囲」ではなく、
ブラウザが内部で持っている枠に貼り付く決まりになっている。
スマホのアドレスバーの出入りや、画面を拡大したときに枠と見える範囲がずれると、
ボタンが下にはみ出して**スクロールしないと出てこない**状態になる。

## 出題パターンで絞る（テストを短くする）

**同じ聞かれ方の問題が何問も並んでいると、テストが長いだけで身に付かない。**
JSON は41問のうち「単語 → 値」が7問、「単語 → キー」が6問あった。

そこで2段階で絞る。**絞り方は分野ごとの生成スクリプトに書く。**

1. **本が違うだけの同じ問題を1つにまとめる**（提示物・聞かれ方・答えが同じもの）。
   残したほうの `from` に、まとめた問題番号を全部入れる
2. **同じ出題パターンは上限まで**（いまは3問）。あふれた分は外す

外した問題は `out/full/not_used.csv` に理由つきで載せる。
**`from` にぶら下がっている別の本の問題も、一緒に載せる**（載せ忘れると全問カバーの見張りに引っかかる）。

### 出題パターンが消えていないか、毎回確かめる

| 名前 | 中身 |
|---|---|
| `spec.patterns` | 本にあった出題パターンの一覧（**絞る前に数えたもの**） |
| `spec.pattern(q)` | 過去問1問 → そのパターンの名前 |

パターンが消えていても、見覚えのないパターンが増えていても止まる。

### 絞り方は `scripts/trim.js`（どの分野でも使える）

### 分野として立てず、「そのほか」に入れるとき（2026-08-21 オーナー）

**決め方が1つしかなく、本の問題も同じものばかりの題材は、分野にしない。**
分野にすると、練習もテストも同じ問題がくり返し出るだけになり、
中身ではなく「その言葉が見えたら選ぶ」という形で覚えてしまう。

最初の例が「ログの読み取り」。本には3冊で3問あるが、提示物も答えも同じ1問だった。
判定ルールも1本しかないので、練習で作る問題も全部同じ答えになっていた。

やったこと。

1. 本の3問を1問にまとめる（残した問題の `from` に3つとも入れる）
2. その1問を `q/misc.js` へ移す
3. 「そのほか」（`types/misc.js`）に、見る所と判定ルールを1つずつ足す
4. `types/log.js` と `q/log.js` を消し、`gen.js` `questions.js` `index.html` `app.jsx` から外す

「そのほか」は**その場で作り直せる問題を持たない**分野なので、
説明の1枚だけが出て、テストには本の問題がそのまま出る。それでちょうどよい。

## 誤答が足りないとき（本の誤答を借りる）

決め方が1つしかない分野は、答えの顔ぶれも1つになる。
そのままだと選ぶものが1個しか出ず、問題として成り立たない。

**そこで、同じ分野の本の問題が出している「正解でない選択肢」を借りる**
（`engine.js` の `spareWrongs()` / `padOpts()`）。

- **こちらで誤答を考え出さない。**借りるのは本の言葉だけ
- その分野で正解になっている文と、`same` に載っている言い換えは、誤答にしない
- 本によって「〜する」と「〜します。」が混じっているので、
  **句点で終わらない言い方を先に使う。**混ぜると、言い回しの違いだけで正解が当てられてしまう
- 借りるのは選択肢の文だけ。問題文と提示物は借りない
  （練習に本の問題そのものを出さない、という決まりは崩れない）

`node selftest.js` が、**こちらで作る問題の選択肢が3つ以上あるか**を毎回見張る。
本の問題（`kind:"past"`）は数えない。**本が2択で出しているものは、そのまま出す。**

## 規則で出せない問題の扱い（bookOnly）

判定ルールでは答えが出せないが、**問題としては出せる**ものがある。
例：`{"apple": ["red", 1]}` で「apple は何を表しますか」。選択肢が
配列／オブジェクト／番号／文字列 で、「キー」が無い（本は文字列を答えにしている）。

こういう問題は `spec.bookOnly = ["B2-0031-03", …]` に入れる。

- **判定の検査からだけ外す。問題はテストに出る**（取りこぼしを作らない）
- 答え合わせは、本の解説だけが出る（見た所と数字は出ない）
- `spec.dropped`（本の答えが矛盾していて使えない）とは別物。混ぜない
